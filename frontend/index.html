    Filters

    Name them in the question, or send them as request fields: drug, condition, sponsor, country, phase, status, and a start-year range.

    Boundaries

    • Trends count trials by start year only.
    • Answers describe registrations, not efficacy or safety.
    • Conditions the registry filters cannot express (for example, randomized or adult-only) are not applied. The answer says so.
    • Broad searches above 20,000 matches can use a 3,000-record sample. The subtitle says so.
    • A network edge means two entities appear in the same trial, not that they were given together.
    • No forecasts, and no granularity other than years.

    How a question becomes a chart
    
      
    The model plans the query. Code fetches registry records, counts them, and builds a chart with sources for every datum.
    
      
    CodeLLMRegistry / cacheUnsupported exit
    
      
    Request path
    
      
    
        
    
          
    Request
    POST /query with a QueryRequest.
    Required: query, 1 to 500 characters.
    
          
    Optional hints: drug_name, condition, sponsor, country, phase, status, start_year, end_year.
    Errors: 422 invalid request or invalid plan after hints; 502 planner or registry failure; 504 registry time budget exceeded.
    
        
    
        
    
          
    Planner (LLM) gpt-5.4-mini
    OpenAI Structured Outputs: strict JSON schema → QueryPlan.
    Pydantic checks rules; one repair retry with validation errors.
    Constraints no filter can express go to ignored_constraints.
    
          
    Unsupported exit
    supported=false → status unsupported.
    Reason in meta.notes. No registry call.
    
        
    
        
    The LLM never sees registry data and never writes a number
    
        
    
          
    Apply hints
    Structured hints override the plan filters.
    A hint for the compared field is skipped with a note. A hint that makes the plan invalid returns HTTP 422.
    
          
    Plan fields: supported, unsupported_reason, analysis, group_by, measures, filters, comparison, top_n, ignored_constraints, interpretation_notes.
    Analysis: breakdown, trend, network, histogram, scatter, total.
    
        
    
        
    
          
    Entity check
    Count each drug, condition, and sponsor name in the registry.
    Fewer than 20 matches: ask the registry's autocomplete, and switch to a name with 10× more trials.
    
          
    "pembrolizimab" (3 trials) becomes "pembrolizumab" (3,006), with a note. Code decides from registry counts; the LLM is not involved.
    
        
    
        
    
          
    Compiler
    Plan → ClinicalTrials.gov search parameters.
    One search per compared value; select only needed API fields.
    
          
    Each compared value becomes its own series. A trial matching several values can appear in each series.
    
        
    
        
    
          
    Retriever CTGovClient
    Picks the exact method with the fewest requests: one count per phase/status/… bucket, or every record up to 20,000 (a 3,000-record sample above that). A total needs only totalCount and a few citation records.
    Token bucket under the measured limit (0.8 request/s, burst 8); retry with backoff. Identical concurrent fetches share one request.
    90 s registry budget per request, then HTTP 504.
    
          
    
            
    In-memory cache
    1 hour, at most 512 entries (least recently used are evicted). A hit reuses saved records.
    
            
    miss ↓
    
            
    ClinicalTrials.gov
    Registry API. Bursts can return HTTP 429.
    
            
    Records and counts return to the retriever; results are cached.
    
          
    
        
    
        
    
          
    Field registry
    Extract and normalize each dimension. Drugs and conditions map to MeSH only on evidence of identity (same words, or a name the sponsor gave); otherwise the free-text name is the label.
    Attach {nct_id, field, excerpt, title, match} to each value.
    
          
    The excerpt is the exact value at the cited API field path. match is exact, alias, broader, or free_text. A derived duration cites both dates.
    
        
    
        
    
          
    Aggregator
    Counts, cross-tabs, yearly trends, networks, bins, scatter points, total.
    Every group keeps its citations.
    
          
    Networks can be bipartite or co-occurrence. A total uses the registry's totalCount. A breakdown by phase, status, study type, sponsor class, or intervention type can use one registry count per bucket. Other analyses count fetched records.
    
        
    
        
    
          
    Chart selector
    Fixed rules map the plan shape to a chart type.
    The LLM does not choose the chart.
    
          
    bar_chart, grouped_bar_chart, time_series, histogram, scatter_plot, network_graph, metric
    
        
    
        
    
          
    Spec builder
    Write visualization {type, title, encoding, data} and meta.
    Each datum has up to 5 trial citations and citation_count.
    
          
    Meta: plan, filters, api_query, count_method, bucket_clauses, data_timestamp, total_matching, trials_counted, count_completeness, records_fetched, coverage per series, entities, ignored_constraints, derivations, multi_valued, units, sort, notes, and LLM cost.
    
        
    
        
    
          
    Contract check
    Pydantic validates the response before it is sent.
    Typed rows, required channels, nonnegative integer counts, citation_count equal to the count, edges that reference real nodes.
    
          
    A spec that breaks the contract is never returned, so a renderer can trust the fields it reads.
    
        
    
        
    
          
    Frontend
    D3 renders each chart type from encoding and data.
    Click a mark to see its citations.
    
          
    The Ask tab shows the chart, source panel, and caveats. The API response tab shows the complete JSON the backend returned.
    
        
    
      
    

      
    How the system is evaluated
    
      
    
        
    Golden dataset
    34 hand-written + 45 synthetic development cases, and a separate 15-case adversarial set.
    TASK.md appendix, taxonomy, edge cases, regressions. Synthetic tuples: intent × entity × filter × phrasing style. Code derives expected plans; gpt-5.4 writes only question text.
    
        
    
          
    Planner evals
    Deterministic plan checks.
    pass@k and pass^k, k=3; 95% Wilson intervals.
    Per intent, failure categories, cost per success, p50/p95 latency.
    
          
    End-to-end evals
    Full pipeline against the live registry on the 34 hand-written cases.
    Check chart type, citations, and meta invariants.
    
        
    
        
    Gates
    GitHub CI: lint and offline tests on every push.
    Local gate: planner_eval --runs 3 --gate uses the key in .env and fails if an intent falls below its floor in evals/thresholds.json. Run before changing the prompt, plan schema, or model.
    --heldout scores the 15 adversarial cases with both evals. That set is never used to tune the prompt.
